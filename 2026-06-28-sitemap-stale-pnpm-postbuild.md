# Production sitemap silently frozen — pillar pages never reached `sitemap.xml`

**Date:** 2026-06-28
**Project:** A Next.js interview-prep web app I work on (consumer SaaS, pnpm monorepo deployed on Vercel)
**Stack:** Next.js 16 · pnpm 11.0.8 · next-sitemap (postbuild hook) · Vercel
**Severity:** SEO — all four pillar pages (`/cv`, `/interview`, `/institution`, `/maganghub`) absent from the production sitemap; the #1 organic landing page (`/cv`) among them. Silent (no error, no alert).
**Time to root cause:** ~20 minutes, during a planned SEO audit (not via an incident)
**Resolution:** Move sitemap generation into the build chain + untrack the stale committed artifacts (`apps/web`, commit `82638d1`)

---

## TL;DR

**The bug:** `https://www.example.com/sitemap.xml` had not changed since **PR #537**. Every page added after that — including the entire pillar-landing set (`/cv`, `/interview`, `/institution` from PR #565, and `/maganghub`) — was missing from the sitemap. `robots.txt` was frozen the same way (missing the `/_m/*` disallow that the current config defines).

**The cause — a two-sided lock:**
1. **Generation side:** `next-sitemap` was wired *only* as a `"postbuild"` npm lifecycle hook. **pnpm (v7+) does not run `pre`/`post` lifecycle scripts by default** (`enable-pre-post-scripts=false`, and there was no `.npmrc` overriding it). Vercel's build command is `pnpm build`, whose script ends at `next build` — so `postbuild` **silently never ran in CI**. The generator had effectively been dead since the repo moved to pnpm.
2. **Artifact side:** `public/sitemap.xml` and `public/robots.txt` were **committed** to git (so a stale file always shipped and served) **and** listed in `.gitignore` (added later). Because they were committed *before* the ignore rule, git kept tracking them — but the ignore rule meant any **local** regeneration **never showed up in `git status`**, so a developer running a build locally would never see a diff to commit. The file could only ever go stale.

Generation never ran in CI; staleness was invisible locally. Frozen from both ends.

**Why nobody noticed:** there is no error when a sitemap is stale. Worse, `/cv` **ranked anyway** (~13,600 impressions / avg position ~5.6 in the 28 days before discovery) — Google found it via internal links — so the one symptom that might have raised a flag (a key page not ranking) never appeared. The omission was pure silent opportunity-cost.

**The fix:** move generation into the build chain so it's deterministic regardless of the pnpm hook —
`"build": "… && next build && next-sitemap"` — and `git rm --cached` the two stale artifacts so the per-environment generated files (already gitignored) become the only source of truth. Verified locally: `next build && next-sitemap` now emits all four pillar pages and a `robots.txt` with the `/_m/*` block.

## How to remember this (plain-language mental model)

A sitemap that's wrong throws no error. A build step that's skipped throws no error. A committed file that's also gitignored throws no error. Stack three silent conditions and you get a file that has been lying to Google for months while every dashboard stays green.

The specific trap: **a `postbuild` hook is not a build step — it's a *convention* that only some package managers honor.** npm runs `pre`/`post` scripts automatically; pnpm (since v7) does **not**, unless you opt in. The moment a repo switches npm→pnpm, every `pre`/`post` hook silently goes dark, and nothing tells you. The hook *looks* wired (it's right there in `package.json`), so everyone assumes it runs.

The second trap compounds it: the generated file was **committed AND gitignored at the same time**. That combination is uniquely dangerous — committing means a stale copy always ships; gitignoring means fresh copies are invisible in `git status`. Neither alone would freeze the file. Together they guarantee it.

**One-sentence version:** the sitemap was generated by a hook pnpm doesn't run, and served from a file git both ships and hides — so it could only ever be stale, and a stale sitemap is silent.

## Symptoms (how it surfaced)

This was found during a deliberate SEO audit, not reported as an incident — which is itself the point: a stale sitemap has no user-facing symptom.

1. A technical-SEO sweep of the codebase noted that `next-sitemap.config.js` `additionalPaths` listed `/cv`, `/interview`, `/institution`, `/maganghub`, but flagged that the *committed* `public/sitemap.xml` appeared to contain only older routes.
2. Fetching the **live** sitemap confirmed it: `https://www.example.com/sitemap.xml` returned home, `/about`, the `/how-to-use/*` set, `/frequently-asked-questions`, `/terms-and-policy`, `/auth/login`, and a stray `/apple-icon.png` — **and none of the four pillar pages.**
3. The live `robots.txt` was missing the `/_m/*` disallow present in the config — confirming it was frozen by the same mechanism, not a one-off.

The tell that made it confusing at first: `/cv` was simultaneously **the single highest-traffic organic page on the site** and **absent from the sitemap**. A page can't be both "winning search" and "excluded from the sitemap" unless the sitemap is being ignored as a discovery source — which is exactly what was happening (Google discovered `/cv` via internal links instead).

## What made this hard

- **No error, anywhere.** A skipped build step, a stale artifact, and a wrong sitemap each produce zero diagnostics. Every CI run was green, every deploy succeeded, every dashboard was healthy.
- **The config was correct.** `next-sitemap.config.js` listed all four pillar pages. Anyone "fixing the config" would have changed nothing — the fault was three steps downstream in *whether and how* the config was executed and shipped.
- **The masking symptom pointed the wrong way.** The page most likely to scream "I'm not indexed!" (`/cv`) was instead quietly ranking, because its internal-link graph carried discovery on its own. Strong resilience, terrible observability.
- **The hook *looks* wired.** `"postbuild": "next-sitemap"` is right there in `package.json`. Nothing about reading the file reveals that pnpm silently declines to run it.

## Investigation (what each check proved)

The root cause was reached by checking the deploy wiring rather than assuming the config was the problem.

| Check | Command / source | Finding |
|---|---|---|
| Is the sitemap tracked in git? | `git ls-files public/sitemap.xml` | **Yes** — committed, not purely generated |
| When was it last regenerated? | `git log -- public/sitemap.xml` | Last touched in **PR #537** (`00a808e`) |
| When were the pillar pages added to config? | `git log -- next-sitemap.config.js` | **PR #565** (`392291c`) — *after* the last sitemap commit |
| Does the committed file contain `/cv`? | `grep -c "/cv" public/sitemap.xml` | **0** |
| How is the sitemap meant to generate? | `package.json` scripts | Only via `"postbuild": "next-sitemap"` — not in the `build` chain |
| What runs on Vercel? | `vercel.json` | `buildCommand: "pnpm build"` |
| Does pnpm run postbuild? | pnpm version + `.npmrc` | `pnpm@11`, **no `.npmrc`** → `enable-pre-post-scripts` defaults to **false** → `postbuild` skipped |
| Is the file also ignored? | `.gitignore` | **Yes** — `/public/sitemap.xml` + `/public/robots.txt` listed (committed before the rule) |

Each check eliminated an "easy" explanation (stale config? no — config was correct; bad deploy? no — deploys were fine; the *pipeline* was wrong) and converged on the two-sided lock.

## Root cause

### Side 1 — the generator never ran in CI

`package.json`:
```jsonc
{
  "packageManager": "pnpm@11.0.8",
  "scripts": {
    "build": "prisma migrate deploy && pnpm type-check && pnpm lint:strict && next build",
    "postbuild": "next-sitemap"
  }
}
```

`vercel.json`:
```json
{ "buildCommand": "pnpm build" }
```

npm automatically runs `prebuild`/`postbuild` around `build`. **pnpm stopped doing this by default in v7** — `enable-pre-post-scripts` is `false` unless set in `.npmrc`. There was no `.npmrc`. So on Vercel:

```
pnpm build
  └─ prisma migrate deploy && type-check && lint:strict && next build   ✅ runs
postbuild (next-sitemap)                                                ❌ never invoked
```

The generator had been dead in CI since the project used pnpm. It would still run for anyone on npm (and presumably did, once, locally — see Side 2), which is why a sitemap existed at all.

### Side 2 — the artifact could only go stale

`public/sitemap.xml` and `public/robots.txt` were both:
- **tracked in git** (committed at some earlier point, before the ignore rule existed), and
- **listed in `.gitignore`** (added later, with the intent "these are build artifacts").

Adding a path to `.gitignore` does **not** untrack a file already in the index. So git kept versioning the committed copy *and* hid every future modification:

- **On Vercel:** the committed `public/sitemap.xml` is served as a static file. Since `postbuild` never runs (Side 1), it's never overwritten. The stale file ships forever.
- **Locally:** if a developer ran a build that *did* regenerate the file, `.gitignore` suppressed it from `git status` — so the fresh copy was never staged, never committed. The stale tracked copy stayed frozen at its PR #537 state.

### The combined effect

The last time the sitemap was (manually/locally) generated and committed was **PR #537**. **PR #565** then added the three pillar landing pages to the config — but with the generator dead in CI and regenerations invisible locally, that config change never propagated to the served file. `/maganghub` (added later still) was never going to appear either. The served sitemap was permanently pinned to a pre-pillar-pages snapshot.

### Why the blast radius was partly masked

`/cv` ranks at position ~5.6 with ~13,600 impressions/28d **despite** the omission, because Google discovered and ranked it through internal links (it's linked from the navbar and every other pillar page). The sitemap is a *discovery and priority hint*, not a ranking requirement — so a strong internally-linked page survives its absence. That masking is exactly why the bug went unnoticed: the page that would have screamed "I'm not indexed!" was instead quietly ranking. The real cost was **slower discovery of new/less-linked pages** (`/maganghub` most acutely, as a time-sensitive campaign page) and a forfeited crawl-priority signal — invisible losses, not visible breakage.

## The fix

`apps/web`, commit `82638d1`:

**1. Move generation into the build chain** (deterministic regardless of the pnpm hook):
```diff
- "build": "prisma migrate deploy && pnpm type-check && pnpm lint:strict && next build",
- "postbuild": "next-sitemap",
+ "build": "prisma migrate deploy && pnpm type-check && pnpm lint:strict && next build && next-sitemap",
```
`&& next-sitemap` runs explicitly as part of `build`, so it executes on every Vercel build no matter what the package manager does with lifecycle hooks. `postbuild` removed to avoid a second source of truth / double-run under npm.

**2. Untrack the stale artifacts** so the (already-gitignored) generated files are the only source of truth:
```bash
git rm --cached public/sitemap.xml public/robots.txt
```
The files stay on disk; git stops tracking them. From now on each environment regenerates its own at build time (`siteUrl` resolves from `NEXTAUTH_URL`, so production emits `https://www.example.com/*` and local emits `localhost`). A stale committed copy can never be served again.

### Why not just add `.npmrc` with `enable-pre-post-scripts=true`?

That would *also* make `postbuild` run — but it's the more fragile fix:
- It re-enables `pre`/`post` for **every** script, a broad side effect to solve one specific need.
- It's invisible action-at-a-distance: the build's behavior depends on a one-line config in a different file that's easy to delete or miss.
- An explicit `&& next-sitemap` in the `build` script is **self-documenting** — anyone reading the build command sees that the sitemap is generated. The lifecycle-hook magic was the original trap; the fix shouldn't lean on more of it.

**Caveat — production not yet fixed at time of writing:** the change is on a feature branch → PR #602 → `develop`. Post-deploy manual steps: in Google Search Console, **resubmit the sitemap** and **URL Inspection → Request Indexing** on the four pillars (priority `/maganghub`, while in-season).

## Lessons learned

### About the bug

1. **A `postbuild` hook is a convention, not a guarantee.** npm runs `pre`/`post` automatically; pnpm (v7+) and some others do not. Any pipeline step that *must* run belongs in the explicit build command, not in a lifecycle hook whose execution depends on the package manager. The npm→pnpm migration silently killed this hook and nothing flagged it.
2. **Committed + gitignored is a staleness trap.** A generated artifact should be *either* committed (and regenerated-and-committed in CI, surfacing in diffs) *or* gitignored (and regenerated at build, never tracked) — **never both**. The "both" state ships a stale file while hiding every fix for it.
3. **Stale ≠ broken, and stale is silent.** There is no error, no 500, no failed check when a sitemap is months out of date. The only signal is absence (pages not getting discovered), which is itself invisible on dashboards. Correctness here needs an active check, not the absence of alerts.
4. **A strong internal-link graph masks sitemap problems.** `/cv` ranking despite its omission is good resilience but bad observability — it hid the defect. Don't infer "sitemap is fine" from "key pages rank."

### About the process

1. **Check the pipeline, not just the config.** The config (`next-sitemap.config.js`) was 100% correct — every pillar page was listed. The instinct to "fix the config" would have changed nothing. The fault was three steps downstream in *how and whether the config was executed and shipped*. When output is wrong but the source looks right, audit the path from source → artifact → served file.
2. **Verify against production, not the repo.** The committed `public/sitemap.xml` and a fetch of the live URL agreed here — but it was fetching the *live* file that made the omission undeniable and ruled out "maybe my local copy is just old." Always confirm the served artifact.
3. **`git ls-files` + `git log -- <file>` is a fast staleness probe.** "Is this tracked?" and "when did it last change vs. when did its inputs change?" immediately exposed that the artifact predated the config that should have produced it.

### Prevention / detection

- **Move all must-run steps into the explicit build command** (done for sitemap). Audit `package.json` for any other `pre*`/`post*` hooks the project relies on under pnpm — they may be silently skipped too. (`postinstall: prisma generate` *does* still run, because pnpm runs `postinstall` for the project's own package; the `pre/post`-of-arbitrary-scripts rule is the one that bites.)
- **Don't commit generated artifacts that are also gitignored.** Pick one model. For sitemap/robots, gitignored + build-generated is now the chosen model.
- **Consider a lightweight CI/monitoring check** that fetches `/sitemap.xml` post-deploy and asserts the pillar URLs (and expected count) are present — turns a silent staleness class into a loud failing check.
